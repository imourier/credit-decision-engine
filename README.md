# credit-decision-engine

A small consumer-credit decision engine on synthetic data: knock-out rules,
weighted scoring that renormalises over missing inputs, a limit band capped by
payment capacity, and a decision record that stores everything needed to
reproduce and audit the result.

Python 3.11+, standard library only. pytest for the tests.

## Pipeline

```
applicant ──> knock-outs ──> scoring ──> limit ──> Decision record (JSON)
               first fail     blocks      band by score,
               stops          renormalised capped by capacity
```

| Module | What it does |
| --- | --- |
| `rules.py` | Six hard rejects in a fixed order, each with a reason code. The first failure stops evaluation. |
| `scoring.py` | Three weighted blocks (bureau, income stability, behaviour), each a weighted average of variables mapped to 0–100 points. |
| `limits.py` | Limit band chosen by score, then capped so that total debt service stays within a share of verified income. |
| `decision.py` | Runs the three stages and returns a `Decision` with inputs, rule outcomes, block and variable scores, effective weights, limit detail and versions. `replay()` recomputes a decision from its own record. |
| `synthetic.py` | Seeded generator of correlated synthetic applicants, with realistic missing-data rates. |
| `cli.py` | `python -m credit_decision_engine --n 20` |

## Design choices

**Knock-outs before scoring.** Some conditions rule out lending whatever the
score says: legal age, fraud, an open default, no verifiable income. Running
them first means the score is only ever computed for eligible applicants, and
a rejection has one unambiguous reason, the first rule that failed. The record
also shows which rules were never reached.

**Renormalise, don't impute.** When an input is missing, the variable is
dropped and the remaining weights in its block are rescaled; an empty block is
dropped and the block weights are rescaled. An imputed value is a number no one
observed, and for a thin-file applicant it is a statement about other people.
With renormalisation every point of the score traces back to an observed input,
and the record shows exactly what was dropped and which weights were used. If
fewer inputs should mean a more conservative outcome, that is a policy rule to
write explicitly, not a side effect of a made-up value.

**Store the inputs with every decision.** Bureau data, income and behaviour
change over time. A decision stored without its inputs cannot be explained
later. Each record carries the input snapshot, the policy and engine versions
and every intermediate result; `replay()` recomputes it and must match. A
mismatch means the inputs were altered or the policy changed.

## Run

```
python -m credit_decision_engine --n 20 --seed 7
python -m credit_decision_engine --n 5 --json
pip install pytest && python -m pytest
```

## What this is not

- Not a statistical model. Weights and breakpoints are set by hand; there is no
  training, calibration or validation against outcomes.
- No real data. Every applicant is generated by `synthetic.py`.
- Parameters are illustrative. Thresholds, weights, bands, rates and amounts
  are invented to make the mechanics visible, in generic currency units.
